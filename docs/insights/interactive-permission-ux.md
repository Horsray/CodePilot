# 交互式提问不该「等你等到超时」

> 技术实现见 [docs/handover/interactive-permission-ux.md](../handover/interactive-permission-ux.md)

## 用户问题

用户在会话里看到 AI 抛出选项卡片（"你要 A 还是 B"），这时切去别的窗口回个消息、查个资料，几分钟后切回来 —— **卡片没了，这一轮对话也结束了**。

更让人困惑的是：AI 有时会重新发一遍同样的卡片。用户此时的感受是「这东西是不是坏了」，而不是「我超时了」。用户的追问很直接：

> 我不理解，这个为什么要做超时呢？我切换回来，就没看到选项卡片啊

而且他说得对：**同类软件没有这个 bug**。在 Cursor、Claude Code 里，等待用户确认的状态可以一直挂着，用户什么时候回来，什么时候继续。

## 为什么会有超时（原来的设计善意）

超时不是为了让卡片消失，而是为了**防止悬挂**：如果 AI 抛出提问后用户永远不回答（走开、切走、去做别的事），服务端内存里的等待 Promise、SSE 连接、`waiting_permission` 运行时状态会一直占着，SDK 子进程被占死，这个会话之后就发不了新消息了。

所以加兜底是对的。**错的是兜底的对象。**

## 核心判断：「等人工」不等于「卡死」

把三把超时铡刀摊开看：

| 超时 | 想防的是 | 实际误杀的 |
|------|---------|-----------|
| 权限注册表 5 分钟自动拒绝 | 用户不回答导致悬挂 | 一个正在看资料的正常人 |
| 流看门狗「无进度即中止」 | 模型上游卡死 | 模型正老实等着用户点选 |
| 前端空闲超时 | 连接断了 | 连接好好的，只是没人说话 |

这三种状态在**工程上**长得很像（都是「一段时间没有任何事件」），但在**语义上**完全不同：

- 模型上游卡死 —— 没有任何一方在等，应该判失败
- 等用户操作 —— **有一方正在等另一方**，这恰恰是正常状态

把它们塞进同一个「空闲超时」里，等于把「人工延迟」当成了「故障」。所以修法不是调阈值，而是**按请求性质分流**：交互式工具（`AskUserQuestion` / `ExitPlanMode`）本来就以「等人工」为存在意义，这类请求的等待时长应由人决定，只由「用户作答」或「这一轮确实终止」来结束。

## 桌面端的媒介属性：状态必须能跨越「窗口不在前台」

这一层常被忽略：**桌面端是「进行态」媒介**。用户不会盯着一个窗口不动，切出去一会儿是常态，不是异常。

这意味着任何「对话状态」都必须能在窗口失焦、被遮挡、甚至渲染进程被后台节流之后**原样恢复**。而原来的实现里，卡片只活在内存快照一处 —— 快照一被清空，就再没有第二条恢复路径（刷新页面也不行），哪怕数据库里那条 `pending` 记录还好端端躺着、接口也早就写好了，只是没人调用。

「卡片可恢复」不是锦上添花，而是桌面端的基本要求：状态不能只有一份、且只在这一屏。

## 取舍

- **没有完全去掉超时**：非交互的工具权限（如危险 Bash 命令）仍保留 5 分钟兜底 —— 那类等待确实可能因为流程异常而悬挂，没有「有一方正在等」的正当性。
- **给等待绑定了流生命周期**：等待不再靠「墙钟」结束，而是靠「这一轮是否还会继续」。用户手动停止、会话被替换、连接断开 —— 这些才是等待该结束的真实信号。
- **恢复是尽力而为**：页面刷新会断开 SSE，服务端此时把这一轮判为终止、pending 落库为 `aborted`，恢复机制也就无从生效。这是「连接即会话」架构的既有边界，不在本次修复范围。

## 未来方向

- **Bridge（IM 渠道）的问答卡片**：目前 IM 侧只能 Allow/Deny，无法真正选选项，需要各平台的交互卡片（Telegram inline keyboard、飞书 interactive card）才能对齐桌面体验。
- **显式告知等待状态**：比起「默默等」，更好的产品表达是让用户知道「我在等你，不会自己走」—— 例如卡片上标注「已等待 N 分钟」。
- **可发现性**：如果确实需要终止一个久悬的等待，应该由用户显式操作（「取消提问」），而不是由系统替他决定。

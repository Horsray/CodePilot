# 交付折叠 — 产品思考

> 技术实现见 [docs/handover/delivery-collapse.md](../handover/delivery-collapse.md)
> 上游相关：[工具调用 UX 优化](./tool-call-ux.md)

## 解决了什么用户问题

### "我要的是结论，不是过程"

Agent 类产品有个天然的叙事结构：过程是给"信任"用的，结论是给"使用"用的。

在长工具链任务里（读 8 个文件、跑 3 条命令、改 2 处代码），对话流会先长出一大坨过程，最后才在底部蹦出结论。这带来两个实际问题：

1. **结论被推到屏幕外**。过程越长，用户越要往下滚才能读到真正要的东西。滚动本身不痛苦，痛苦的是"我不知道还要滚多久"。
2. **回看时找不到结论**。隔天回到这个会话，一屏之内看不到答案在哪，得在几十行工具调用里翻。

之前 [工具调用 UX 优化](./tool-call-ux.md) 已经解决了"过程看不清"（thinking 展示、工具归组、错误标红）。这次要解决的是**反过来的一面**——过程看得太清楚了，以至于挡住了结论。

**方案**：一轮任务**彻底结束之后**，把过程整体收成一条 `N个已完成 · 思考与执行完毕` 的汇总条。屏幕上只剩结论。

## 为什么这样设计

### 触发点：任务跑完才收，任务进行中全程铺开 —— 这一条返工过两次

**最初的判断（错的）**：等任务跑完才收，收的那一下会是个大跳变；不如在"第一个结论字出现"时就收，趁用户注意力从过程区移到结论区的空档，让过程在余光里平滑收拢。

这个判断本身不荒谬，但它依赖一个隐含前提：**"第一个结论字出现"意味着任务快结束了**。实现时复用了代码里现成的 `isSummarizing`（原本用于显示一句"任务已完成，开始总结"的提示），以为它就是那个意思。

**它实际的意思是"此刻没有工具正在跑"** —— 多步任务里每两个步骤之间都成立（上一批工具跑完、下一批还没发起）。后果是任务刚开头过程块就被收起，而且因为实现上"收起这个动作只认一次边沿"，翻回去也不会再展开 —— **整轮任务永久停在折叠态**。

用户的反馈非常直接：*"任务从一开始所有的消息就被折叠了，折叠区在显示步骤……算了，最后都完成了再折叠吧，你这做的完全不能用。"*

**修正后的判断**：任务进行中必须全程铺开，收起的时机是"任务彻底完成"。

这个修正还顺带解决了一个原本要妥协的问题。原方案为了保住收起动画，必须让手风琴形态从流式一开始就常驻，**代价是流式期间多一条汇总头行**。改成"完成后才收"之后，收起发生在消息落定那一刻、本来就不播动画，流式侧可以干净地铺开，连头行都没有了 —— 用户看到的是一整段没有壳的过程，然后它整体收成一条。

**三条可以复用的教训：**

1. **复用一个现成变量当触发器之前，先确认它的语义真的是你要的那个。** `isSummarizing` 用来插一句提示是安全的（幂等、无破坏性），用来收起一大块内容就致命了 —— 代价的量级完全不同。
2. **破坏性的、不可逆的 UI 变换，不要挂在可能高频翻转的信号上。** 要么让它在挂载那一刻定死（现在的做法），要么等一个真正单调的完成信号。
3. **当"正确"和"优雅"冲突时，先把正确做出来。** 这次为了动画让步的复杂度（常驻手风琴、高度折算时长、交棒继承展开态）在修正触发时机后全部变得不必要，删掉之后代码反而更短。

### 为什么合成一条汇总条，而不是保留 N 条工具行折叠

Trae / Cursor 之类的做法是把每个工具组各自折叠，留下 N 个小条。视觉上是"折起来了"，但屏幕上仍有 N 个元素。

这里要的是"只交付结论"，那就只留**一条**。折衷是牺牲了"跳着看某一步"的能力——但那个能力已经被"点开看全部"覆盖了，而且这是回看场景，不是实时场景。

### 为什么手动展开记忆是"单轮级"而不是"会话级"

这是我最初判断错的地方。

我原本设计成会话级：用户手动展开过，这个会话内就不再自动收起——理由是"避免和用户抢控制权"。

用户的实际反馈推翻了它：**"用户展开以后，下次发消息，还是自动折叠"**。

想明白了：如果记忆是会话级的，用户在一次长会话里展开过一次，之后每一轮回复都会把整坨过程铺在屏幕上，直到会话结束——这正是这个功能想解决的问题本身。用户的意图不是"我讨厌折叠"，而是"**这一轮**我想看看它干了什么"。下一轮他会带着同样的好奇重新决定。

所以记忆的粒度应该是"轮"（turn），不是"会话"（session）。这个粒度概念上也更对：一轮 = 一次交付 = 一次"过程 → 结论"的叙事。

### 为什么一定要"丝滑"（用户的硬性要求）

用户明确强调了两遍"动画要丝滑顺畅"。这不是审美洁癖——**折叠这个动作，本质上是在用户眼皮底下移除屏幕上的大部分内容**。任何一丝卡顿、跳变、文字被压扁，都会被读成"出 bug 了"或"内容丢了"。

修正触发时机之后，动画的用武之地变得很明确：**用户手动开合的时候**（点开看过程、看完再收起来），以及交付那一刻的"挂载即定型"（不需要动画，因为内容本来就在那个位置，收起来是静止的干净形态）。

手动开合上仍付了一笔成本：**收起用了和展开不同的缓动曲线**。项目统一的入场曲线是强 ease-out，位移集中在开头。拿它收一个上千像素高的过程块，视觉上像被"抽走"——一眨眼就没了，剩下的时间在等。改成先加速后减速，才有"落下去"的手感。

（在错误的触发时机下，这部分设计复杂得多：时长要按内容高度折算、手风琴形态要为了拿到动画起点而从流式一开始就常驻、还要跨组件继承用户的展开状态。修正时机后这些全部不必要，一并删掉了 —— 见上文"三条可以复用的教训"第 3 条。）

### 为什么做成可关闭的设置项

折叠是个有观点的默认值，不是客观正确。有人就是喜欢看过程在眼前滚动——那是"AI 在工作"的安全感来源，砍掉它是剥夺。所以默认开启 + 设置里一键关闭，而不是写死。

## 一个被接受的取舍

中段文字（正文与工具调用交替时，模型写给用户看的中间说明）也跟着一起被收进汇总条。严格说这是"误伤"——那些文字本来就是给用户看的。但它和工具调用在同一个容器里，割开需要重构渲染层。

判断是：交付之后，用户真正要的是最后的结论；中间说明是"过程"的一部分，和工具调用一起被收走是符合直觉的。如果后续有用户反馈"我的中间说明不见了"，再单独把文字块提出来。

## 未来可能的方向

- **区分"过程"与"交代"**：把工具调用之间写给用户的文字块从汇总条里摘出来，只收工具调用。需要渲染层结构调整。
- **等待中的感知**：目前收起后就是干净的结论。如果这一轮特别长（比如 3 分钟、40 次工具调用），或许汇总条上可以带一点"跑了 40 步"的量化信息，让等待有实感。现在的 `N个已完成` 已经是雏形。
- **不同任务的默认策略**：快速问答其实不需要折叠（本来就没过程）；长任务才需要。可以按"工具调用数量阈值"自动决定，但阈值又难调，暂时不做。

## 已知局限

- **旧格式消息不会被折叠**。"这一轮给出结论了吗"是靠解析消息里的 text block 判断的；历史上有些消息把结论存成了 `thinking` block，解析不到 text block，于是被判成"没跑完"，保持展开。这类消息本来就该"没结论就别藏过程"，所以不算错，但新旧消息的形态会不一致。
- 设置项文案目前是中文硬编码，与相邻的「提示音」行一致，**未走 i18n**。若要面向多语言用户需补齐。

# 手机端要的是结论，不是过程

> 技术实现见 [docs/handover/bridge-final-response.md](../handover/bridge-final-response.md)

## 用户问题

2026-10-07 用户通过微信桥接让 CodePilot 去服务器上排查一个数据问题。手机上一次又一次收到这样的回复：

```
让我直接在服务器上查一下花生国风空间（xiangyi）的用户数据情况：
SSH 隧道之前已经建立了，让我直接在服务器上查 MySQL：
你说的"用户名"搜索在 /users 页面，我需要确认：MySQL 里 users 表的
```

全是"我准备做什么"，而且最后一句话停在半截。用户的判断非常准确：

> "手机不可能显示流式的思考构成，它把思考过程当结论发给我了，导致对话中断了。
> 应该是只发结论给我，结论发出之前，思考过程不作为消息发送才对吧？
> 或者发阶段性结论，但不能终止任务啊，这都没完成就停了。"

## 为什么会出现"过程当结论"

桌面端和手机端对同一条 AI 输出的消费方式**根本不同**：

- **桌面端**：过程叙述和工具调用卡片交替流式呈现，用户天然把它们读作"正在进行中"。
  过程文本不但无害，反而是重要的进度反馈。
- **手机端（IM）**：一条没有上下文的纯文本消息，用户只能把它读作**最终答复**。
  推送到达的那一刻，它就"定型"了。

而桥接层原本是"照搬桌面端的一整轮文本"，于是桌面端的过程叙述在 IM 里就变成了
"AI 一直在说它要做什么，却什么都没给我"。

**关键洞察：IM 是"完成态"媒介，桌面是"进行态"媒介。** 把进行态的内容直接投递到完成态
媒介里，用户读到的一定是错误语义。

## 为什么选"只发结论"，而不是"发阶段性进展"

用户给了两个选项，我们选了前者（并在中断时兜底）。理由：

1. **微信是强打断的场景**。每一条消息都是一次通知震动。一次任务发 5 条进展，
   体验上是"被骚扰 5 次"，而不是"获得了 5 次进度"。
2. **过程叙述本身没有信息增量**。"让我查一下 MySQL" 对用户来说不是进度，
   只是模型的自言自语——真正的进度是"MySQL 里没有这个用户"，那是结论的一部分。
3. **阶段性结论不等于阶段性叙述**。如果模型确实产出了"已排除 A、B 两个原因"这种
   有信息量的中间结论，它会落在最后一段文本里，被"只发最终结论"保留下来。

不过认知上是诚实的：**这个选择牺牲了长任务的实时感**。一个跑 5 分钟的任务，
用户在这 5 分钟里什么都收不到。这是当前方案的代价，也是未来可以做的方向（见下）。

## "不能终止任务"其实暴露了另一个问题

用户抱怨"没完成就停了"，表面看是"消息发早了"，实际是**两个问题被打包在一起**：

| 用户感知 | 真实机制 |
| --- | --- |
| 收到的消息像过程 | 整轮文本被拼接后投递 |
| 消息停在半句 | 模型"说要做"却没调用工具就 `end_turn`，这一轮真的结束了 |

第二个问题是**模型行为**（deepseek 等中转模型在长链工具调用中容易提前收尾），
桥接层原本无从干预。我们加了"检测到未完成就自动接着跑"的兜底，
本质上是**替模型把话说完**。

这里的设计原则是：**宁可多跑一轮，也不要让用户以为任务结束了**。
因为"以为结束"的代价是用户重新组织语言再问一遍——而正确答案其实已经差一步了。

## 已知的局限与未来方向

- **静默期偏长**：只发结论意味着长任务期间手机端完全安静。可能的改进方向是
  用 IM 平台原生的"正在输入"状态（微信/Telegram 都支持）承担进度感，
  既不产生消息条数，又能告诉用户"还在跑"。
- **未完成检测是启发式的**：靠"结论以冒号收尾 + 含前瞻词"判断，可能漏判。
  更可靠的做法是让模型在收尾时显式声明任务状态，但这依赖模型配合。
- **根本解在模型侧**：中转模型提前 `end_turn` 是能力问题，续跑只是补丁。
  如果后续切到更强的模型，续跑触发率应显著下降——这个指标值得观测。

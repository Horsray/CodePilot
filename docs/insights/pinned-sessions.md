# 收藏会话（图钉）— 产品思考

> 技术实现见 [docs/handover/pinned-sessions.md](../handover/pinned-sessions.md)

## 解决了什么问题

CodePilot 的会话列表按**项目目录**分组，排序规则是"最近更新在前"。这个规则对"同时推进多个项目"的用法是对的，但对高频使用的**固定几个会话**不友好：

- 一个活跃项目会不断产生新会话，"我要经常回来的那个会话"会被自己项目的其他会话往下挤，更会被其他项目整体顶下去；
- 目录分组意味着置顶一个会话=置顶整个目录，粒度太粗——用户想要的往往不是"这个项目我都常看"，而是"这个会话我下次还要接着用"。

用户的原话是"方便我直接下次找到它"——核心诉求是**降低回收成本**，不是整理欲。

## 为什么这样设计

### 1. 用图钉，不用右键菜单

会话行右侧本来就有 hover 才出现的三点菜单。把"收藏"放进菜单里会更"整齐"，但收藏是一个**高频轻动作**——它应该和"点开会话"一样顺手。独立的图钉按钮：

- 未收藏时 hover 出现（与三点菜单同一时刻），不打扰；已收藏时常驻高亮，让"哪些被收藏了"一眼可见；
- 单击直接完成收藏/取消，不需要"打开菜单 → 找菜单项 → 点击"三步。

代价是行右侧多了个常驻元素，时间戳需要让位——但这个取舍在计划阶段就明确算过（见交接文档的按钮显示规则表）。

### 2. 收藏后从原列表隐藏，而不是两处同时显示

两种做法都能"找到会话"，但语义完全不同：

- **两处显示**：用户看到的是一份"重复的列表"，同一个会话在浏览原项目时出现两次，容易误判"这是两个会话"；
- **原处隐藏**（本方案）：收藏区是**唯一的家**，语义变成"这个会话从工作台上'别'到了胸前的口袋"。取消收藏=放回原处。

选择后者的理由：收藏是"**固定**"（pin）而不是"**快捷方式**"（shortcut）。被固定的东西不应该还散落在桌面上。

### 3. 位置放在「绘影智能体」正下方

「绘影智能体」是用户最高频的入口（助手工作区），它固定在列表第一位。收藏区排在它之后，含义是"**工作区是第一顺位，我亲手标的收藏是第二顺位**"——符合"用户显式意图 > 系统默认分组"的一般直觉，也不会把助手入口挤下去。

对应地做了一个兜底：即使工作区的会话**全部被收藏**（列表里该目录空了），分组头依然保留。否则会出现"把助手会话收藏后，助手入口反而消失了"的荒唐情况。

### 4. 状态必须完整继承

收藏区如果只是"标题列表"，用户就得点回去确认"它跑完了吗"——那收藏反而制造了额外成本。因此收藏区里的行与项目列表里的行是**同一个组件、同一份状态**：运行中转圈、完成蓝点、待批准铃铛全部照旧。用户看收藏区等于看原列表，只是过滤条件不同。

这也是为什么收藏模块由 `ChatListPanel` 注入 `children`（共享 `renderSessionItem`），而不是自己渲染一套简版行——从实现上杜绝"两套 UI 漂移"。

## 取舍与已知局限

- **固定到顶部可以是全局分区**（在列表最顶部做一条独立区域），而不是"跟着工作区分组"。最终选择了后者是因为用户的描述是"绘影智能体**下面**"——用户对位置有明确预期，产品不应自作主张。
- **收藏与分屏（split）互斥**：split 组已有专门的固定展示位，收藏区排除 split 会话，避免同一会话渲染两处。
- **不做收藏排序编辑**：目前按收藏时间倒序（最近收藏在前）。拖拽排序在收藏数量少（个位数）时收益很低，先不引入复杂度。
- **批量操作不含收藏会话**：全选/批量删除作用于原项目列表，与"收藏已从原列表移出"的语义保持一致。若未来用户反馈"想批量管理收藏"，再单独加。

## 未来可能的方向

- 收藏上限提示或分组（当收藏数量大到需要"文件夹"时）；
- 收藏会话的跨设备同步（依赖会话数据本身是否上云）；
- 按"收藏"维度做全局搜索的过滤条件（数据层已经支持，只差 UI 入口）。

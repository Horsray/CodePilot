# 为什么助手会"答非所问"——一次把 SDK 行为当作产品缺陷来修的思考

> 技术实现见 [docs/handover/sdk-injected-turn-suppression.md](../handover/sdk-injected-turn-suppression.md)

## 用户看到的是什么

微信桥接的助手，聊着聊着会冒出一句完全不相干的话：

> 用户：我说的是用户名。你仔细看看代码，基本逻辑搞清楚
> 助手：SSH 隧道任务已完成 📮 还在等你回复呢～ 🐰

或者更隐蔽的版本——正常回答末尾被粘上一句：

> 助手：……（正确的回答内容）
> 　　　后台 SSH 隧道任务已完成 📮 还有什么需要帮你的吗？

用户的第一反应必然是"丢上下文了"。这是一个**信任级别**的问题：IM 桥接的价值在于
"我在微信里也能用上这个助手"，一旦它开始说胡话，用户就会停止使用，而不是去 debug。

## 为什么它不是"上下文丢失"

排查第一件事是推翻最直觉的假设。证据链：

1. SDK session 文件有 805 条记录，`sdk_session_id` 从头到尾没变过 —— **上下文一直在**
2. `scheduled_tasks` 表是空的 —— 不是定时任务自动触发
3. 心跳 auto-trigger 要求 `initialMessages.length === 0` —— 不是心跳唤醒

真正的原因在会话记录里躺着：一条 `queue-operation` 入队记录，紧跟一条**字符串型 user 消息**，
内容是 `<task-notification>`。这是 **SDK 自己注入的合成消息**，不是用户打的字。

## 真正的机制

Claude Code SDK 会把长时间运行的 Bash 命令转入后台，命令结束时往同一条 query 里
追加一条合成 user 消息，并**再跑一轮模型**。这一轮的输出走的是同一条 SSE 流；
而持久会话的流是挂着不结束的，下游就把这轮文本并进了用户回复缓冲区。

**时间戳的巧合是最有欺骗性的部分**：注入回答落库时，时间戳和用户的下一条消息完全相同，
于是从数据库视角看，它精确地"回答"了那个它从未见过的问题。

## 为什么会自我循环

隧道命令写成了 `ssh ... "echo '隧道已建立'; sleep 120"`。

`sleep` 是个定时炸弹：时间一到隧道必断 → 下次重连 → 又一条 task-notification →
又一轮注入回答。"建立隧道"这个操作天然是长期的，却被写成了一个会自己到期的命令。

**这个反模式被写死在技能文档里**（`~/.claude/skills/服务器/SKILL.md` 明确要求
"使用 `run_in_background` 参数后台运行"）。所以这不是模型偶发犯错，
而是**我们自己的工具指引在生产 bug**。修技能比修代码更根本。

## 设计取舍

### 在哪里拦？

三个候选位置：

| 位置 | 问题 |
| --- | --- |
| Bridge 消费端 `conversation-engine.ts` | 只修了微信，桌面端照旧 |
| Chat route `api/chat/route.ts` | 只修了桌面端，Bridge 照旧 |
| **`claude-client.ts` 流源头** ✅ | 一次修复覆盖所有消费者 |

选源头。这也符合已有的分层直觉：流协议层决定"什么是对外可见的输出"，
消费者不该各自判断。

### 抑制整轮 vs. 只标注

可以只给注入轮打个标记、让下游自己决定丢不丢。但下游有三处（chat route、bridge、
useSSEStream），任何一处漏改就漏一次。**默认丢弃 + 显式观测事件**
（`internal_turn_start` / `internal_turn_end`，带 `_internal: true`）
既安全又可排障。

### 一个差点埋进去的坑

最初版本一检测到注入消息就立刻进入抑制态。但注入消息**理论上可能在本轮回答途中到达**
——那时立刻抑制会把**用户自己的回答和 result 一起吞掉**，故障比原问题更严重。

所以加了"挂起"状态：本轮 result 之后再接管。这个问题在当前实测里没出现
（通知都在轮次边界到达），但代价只有几行代码，而失败后果是"用户的问题没被回答"。
**对这种不对称的风险，宁可多写几行。**

## 附带发现：那个「MCP 13 异常」

用户截图里的 `MCP 14/27 · 13 异常` 看起来像一堆服务挂了。实测：

- 逐个做 MCP `initialize` 握手，15 个全局 server **14 个正常**，唯一坏的是
  `WebParser` 的 URL 少了一个 `h`（`ttps://`）—— 一个纯粹的拼写错误
- 剩下的"异常"是把 `pending`（启动中）算进了异常：`npx` 拉起的 server 冷启动要 5~8 秒，
  init 采样时几乎必然还是 pending

**一个指标如果默认显示"大部分东西坏了"，它就不再传递信息**——用户会学会无视它。
所以把 `pending` 从异常里拆出来单列，并做有限轮询等它自己变绿。

## 未来的方向

- **能否不让 SDK 注入？** 目前 SDK 没有关闭 task-notification 的开关。
  根治方向是让 agent 不要写出会自己到期的长命令（技能侧已修）。
- **注入轮本身可能有价值**：后台任务完成是真实信息。现在直接丢弃，
  未来或许应该以"系统提示条"的形式展示，而不是伪装成助手发言。
- **同类风险会复现**：任何"SDK 注入合成消息 → 触发额外轮次"的模式都会有同样问题。
  `detectSdkInjectedUserTurn()` 是唯一的识别入口，扩展它即可覆盖。

## 一句话

用户看到的是"助手在说胡话"，实际是**我们教给 agent 的一条命令写法，
被 SDK 的后台机制放大成了产品级故障**。修代码是止血，修技能才是根治。
